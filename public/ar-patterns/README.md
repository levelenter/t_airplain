# AR.js pattern マーカー（番号入りマーカー 01〜06）

このディレクトリには AR.js（`@ar-js-org/ar.js` の aframe ビルド）用の `.patt` パターンファイルを置きます。
`src/pages/MarkerArView.vue` が `src/utils/markerAr.ts` の `MARKER_AR_MARKERS` を元に
`<a-marker type="pattern" url="ar-patterns/marker_0N.patt">` として読み込みます。

`public/image-targets/`（8th Wall 用）とは別の、独立したマーカー方式です。
写真マーカー（`marker_1`〜`marker_7`）とは名前空間・仕組みとも別なので混同しないでください。

## 元画像とマーカー方式の判定

`public/marker/01.png`〜`06.png`（1240×1653、下部に番号を追加したもの）は、
黒い太枠＋中央に白いブロック図形という構成で、枠内の模様は「バーコード／セルのグリッド」ではなく
連続した自由形状（ArUco 系ではなく ARToolKit 系のカスタム画像パターン）です。実測すると:

- 黒枠を含むマーカー本体（1240×1240 部分の中）: 1008×1008 px、余白（quiet zone）116px
- 黒枠の太さ: 252px（本体の 25%）= AR.js/ARToolKit のデフォルト `patternRatio = 0.5` と一致
- 内側の模様（枠を除いた部分）: 504×504 px

これは ArUco/AprilTag のような「ビット列を読み取るバーコード式」ではなく、
画像そのものを 16×16 グリッドでテンプレート照合する **pattern マーカー**（AR.js の `type="pattern"`、
`hiro`/`kanji` プリセットと同じ仕組み）に適した形式です。6 枚とも外枠が同一のため、
枠だけでは区別できず、内側の白いブロック模様（と今回追加した数字）で区別しています。

## .patt の生成方法

`npx @8thwall/image-target-cli` は 8th Wall 専用で pattern マーカーの `.patt` は作れないため、
AR.js 公式の生成ツール（`three.js/examples/marker-training/threex-arpatternfile.js` の
`THREEx.ArPatternFile.encodeImage`）のアルゴリズムを、同ディレクトリの
`scripts/generate-ar-patterns.mjs`（Playwright で Chromium の Canvas 2D を使って実行する）に移植して
`public/marker/0N.png` から再生成しています。**再生成する場合は
`node scripts/generate-ar-patterns.mjs` を実行してください**（過去バージョンはこのスクリプトを
repo に残していなかったため、生成のたびに手作業でアルゴリズムを再現しており、公式アルゴリズムとの
間に数%のズレが生じていた。今はスクリプトそのものが repo にあるので再現性がある）。

1. `public/marker/0N.png`（1240×1653、上部 1240×1240 がマーカー本体）から内側の模様だけを切り出す
   （黒枠を除いた 504×504 px、オフセット (368, 368)。実測値、`patternRatio = 0.5` と一致）。
2. `THREEx.ArPatternFile.encodeImage` と同じく、0°, -90°, -180°, -270° の 4 方向に Canvas の
   `rotate()` を掛けながら 16×16 の canvas へ `drawImage` で縮小サンプリングする
   （ボックスフィルタではなく、公式ツールと同じブラウザの `drawImage` 補間）。
3. AR.js の `.patt` フォーマット通りに出力: 4 方向 × 3 チャンネル（BGR 順）× 16 行 × 16 個の数値
   （3 桁右寄せ、スペース区切り、方向ブロックの間に空行）。今回の画像は白黒（R=G=B）なので
   チャンネルの並び順は結果に影響しません。

## 懸念点（02〜06 が実機で認識されない問題について）

- 実機で「01 は認識するが 02〜06 は認識しない」報告があり、調査の結果、以下が判明している。
  - 旧 `.patt`（このスクリプトを導入する前のもの）は、公式アルゴリズムを都度手作業で再現していたため、
    厳密な `THREEx.ArPatternFile.encodeImage` の出力と比べて数%（相関係数で 0.96〜0.98 程度）の
    ズレがあった。`scripts/generate-ar-patterns.mjs` 導入によりこのズレは解消した。
  - より本質的な懸念として、6 枚とも外枠の太さ・比率が同一で、内側の模様も「黒枠＋白いブロック」という
    共通の構図のため、16×16 に縮小した後の模様同士の相関が高い（Node で総当たり相関を計算すると、
    別番号同士でも 0.79〜0.80 程度まで上がる組み合わせがある）。ARToolKit のマッチングは総当たりの
    相関に基づくため、この「地の相関の高さ」がそのままマッチング精度の余裕（マージン）の乏しさに
    直結している。01 は 6 枚の中で最も単純な模様で自己相関が最も高く、これが実機で唯一安定して
    認識される理由と推測される。
  - このため `.patt` の再生成だけで 02〜06 の認識が実機で改善するとは限らない。改善しない場合は、
    02〜06 の内側の模様（`public/marker/02.png`〜`06.png` の白いブロック部分）をもっと非対称・
    高コントラストな形状に描き直し、模様同士の相関を下げることを検討してほしい（マーカー画像の
    差し替えが必要になるため、今回のコード修正の範囲外）。
- `.patt` の 4 方向（回転）の並び順は AR.js の生成ツールの回転方向をそのまま踏襲したが、
  実際の物理マーカーの向きとの対応（どの回転が「正面」か）は保証できていない。3D コンテンツが
  90°/180°/270° 回転して見える場合は `?debug=true` の調整パネル（`transform.rotation`）で補正できる。
